# Evaluation analysis

Discussion of the run in [results/report.md](results/report.md). The report is
generated by the harness and is pure data; this file is the reading of it.

Run: 84 queries, `qwen2.5:7b` served locally by Ollama, no API cost.
Reproduce with `python -m eval.run_all`.

---

## 1. Why the multi-agent mode wins, and what it costs

| configuration | n | completion | tool-calls | turns | mean tokens |
| --- | --- | --- | --- | --- | --- |
| `single` | 20 | 65% | 80% | 2.1 | 6,337 |
| `multi` | 20 | 85% | 85% | 4.8 | 7,727 |
| `multi+no-compaction` | 20 | 80% | 90% | 4.7 | 8,332 |

The team spends **1.22x** the baseline's tokens and 2.3x its turns for **+20
points of completion**.

Almost all of the baseline's loss comes from one behaviour, and it is structural
rather than random. Handed pre-retrieved context in its opening prompt, the
single-agent loop frequently decides it already knows enough and answers on a
single turn *without calling `search_knowledge_base` at all*. It did this on
`read-lines`, `tz-convert`, `dataclass-json` and `cross-corpus`, every time at
confidence 0.90–1.00. For `tz-convert` it built an answer around a `KabulTz`
class that happened to appear in a pre-retrieved chunk, rather than searching for
`zoneinfo`.

The planner removes the option. A researcher cannot answer from memory because
issuing a lookup is the only action it has, so the pattern buys grounding by
construction rather than by asking the model nicely.

**Where the cost goes.** On a question that needs no documentation the planner
returns an empty task list and the query drops to the single loop, so the entire
overhead of the pattern is one planner turn. That happened on 3 of 20 queries
(both arithmetic cases and one other). Trajectory length is reasonable against
its ceiling in both modes: 2.1 turns of a possible 4 for the loop, 4.8 of a
possible 6 for the team (planner + longest researcher + synthesiser).

## 2. What compaction actually saved

**7% of tokens** (7,727 vs 8,332 per query), at 85% versus 80% completion.

That is smaller than the mechanism suggests, and the per-query data says why: a
researcher usually issues one or two searches, so there is frequently only *one*
stale tool payload available to compact. The technique is sized for the case it
was built for — a researcher that has to re-query three or four times before it
finds the right page — and most queries in this set never reach it. A corpus with
worse retrieval, or a higher `RESEARCHER_MAX_ITERATIONS`, would show more.

The 85%/80% completion difference between the two rows is a single query and
should be read as noise. Compaction is a cost optimisation; there is no evidence
here that it improves accuracy on well-formed input.

Its real payoff turned out to be elsewhere — section 3.

## 3. Failure injection: the sharpest result

| fed corrupted retrieval | confident answer on bad evidence | admitted the gap |
| --- | --- | --- |
| `single+malformed_retrieval` | **6 / 6** | 0 |
| `multi+malformed_retrieval` | **1 / 6** | 5 |

`malformed_retrieval` replaces every search result with rows whose text is
unreadable and whose metadata is empty. The single-agent loop wrote fluent,
plausible documentation for all six queries at confidence 0.70–0.80:

> *`tz-convert`, `single+malformed_retrieval`, confidence 0.70:* "To build a
> timezone-aware datetime in Python, you can use the **pytz** library along with
> the `datetime` module…"

`pytz` is not in the corpus, was not retrieved, and is not the answer the CPython
3.14 manual gives. This is the textbook cascading soft failure: nothing raised,
the output reads well, and it is built on nothing.

The team answered five of six like this instead:

> *`json-indent`, `multi+malformed_retrieval`, confidence 0.00:* "The findings do
> not provide information about what the indent argument to json.dumps does."

**The cause is the compaction boundary**, which makes this a result about the
context-engineering technique as much as about the agent count. A researcher
looks at the corrupted rows and honestly reports no findings, so the synthesiser
receives the string `(no supporting text was found)` rather than the garbage
itself. Text that *looks* like retrieved documentation invites a model to keep
writing in the same register; an explicit statement of absence does not. Isolating
context protected truthfulness, not just budget — which was not the reason the
boundary was introduced.

The other two faults produced **0 cascading failures out of 6 each**:

- `tool_unavailable` — the researcher never runs, its digest carries
  "search_knowledge_base is unavailable, so nothing could be retrieved", and the
  synthesiser is told the evidence is missing. Mean 1,058 tokens, the cheapest
  configuration in the run, because the system stops early instead of flailing.
- `retrieval_timeout` — the tool returns a message naming the timeout rather than
  an empty list. An empty list reads to a model as "nothing was found", which is
  a reasonable thing to answer from; a timeout is not.

## 4. Weaknesses this run exposed

A report with only good news is not an evaluation.

**The synthesiser over-triggers the calculator.** On `tz-convert`,
`url-roundtrip` and `cross-corpus` it passed prose to a tool that only accepts
arithmetic, and the restricted AST rejected it. No answer was harmed — the error
goes back to the model — but it is three wasted calls, and it is why `multi`
scores only 85% on tool-calls. The fix is to stop handing the synthesiser a
calculator it almost never needs; it was given one so that arithmetic could
survive the research path, which the planner's empty-task-list route already
handles better.

**The schema validator earns its place.** One run invented a `matches` argument
for `search_knowledge_base`. The registry rejected it and the harness recorded an
invalid call rather than letting it pass silently.

**Some failures are the model, not the design.** Both patterns answered
`int-error` with "TypeError" instead of "ValueError", at confidence 1.00, having
retrieved the right page. A 7B model does the reasoning here and no amount of
orchestration repairs a wrong fact stated confidently. This is the
**self-verification paradox** appearing exactly where the design admits it is not
solved: the synthesiser sees findings, never source text, so it cannot check a
researcher's claim — only propagate it. A verifier agent holding the raw chunks
is the fix, and it is not implemented.

**Retrieval, not reasoning, caps the multi-hop scores.** `tz-convert` failed in
every configuration because the second researcher's search for timezone
conversion returns `library/datetime.html` rather than `library/zoneinfo.html` —
`datetime.astimezone` genuinely is the better lexical match for "convert to
another timezone". No agentic structure fixes an embedding that ranks the wrong
page first.

## 5. Scoring decisions worth knowing when reading the tables

- **Pre-retrieved chunks are reported as sources but excluded from grounding.**
  Finding the page is the retriever's job; citing it is the agent's. Counting
  pre-retrieval towards grounding would credit every agent with work it did not do.
- **Tool errors are labelled `arguments` or `infrastructure`.** A calculator
  rejecting "next Tuesday" counts against the agent; a search timing out does
  not. Without that split, an injected fault would score as an agent error.
- **`multi+tool_unavailable` shows 0% tool-calls by construction.** Those cases
  expect `search_knowledge_base` and the fault withdraws it. That is the
  injection working, not the agent choosing wrongly.
- **Declining is detected heuristically** from a narrow phrase list plus a
  confidence floor of 0.2. It is deliberately narrow so it cannot fire on a real
  answer that merely carries a caveat.
